# مستند کامل API پنل ادمین

این سند تمام چیزی که ادمین/اپراتور از طریق پنل ادمین می‌تونه انجام بده رو
پوشش می‌ده: مدیریت کاربران، مدیریت دستگاه‌ها (کیوسک‌ها)، مدیریت محتوا (لوکال
و اسکرپ‌شده)، و مدیریت ویترین هر کیوسک.

> مرجع رسمی و همیشه به‌روزِ اسکیمای دقیق request/response همون Swagger UI
> سرور (`/swagger/index.html`) هست. این فایل برای دیدن **کل نقشه‌ی راه** و
> اینکه چه اندپوینت‌هایی با هم چه فلویی می‌سازن نوشته شده.

---

## ۱. نقش‌ها (Roles) و اینکه هرکدوم چیکار می‌تونن بکنن

سیستم ۴ نقش داره: `admin`, `operator`, `user`, `device`.

| نقش | برای کی | دسترسی خلاصه |
|---|---|---|
| `admin` | مدیر ارشد سیستم | به همه‌چیز دسترسی داره: مدیریت کاربران، دستگاه‌ها، محتوا، ویترین |
| `operator` | اپراتور/تحریریه‌ی محتوا | مدیریت محتوای لوکال + مدیریت ویترین + مشاهده‌ی محتوا. **دسترسی به مدیریت کاربران و دستگاه‌ها نداره** |
| `user` | نقش عمومی/احراز هویت‌شده (فعلاً کاربرد خاصی توی پنل ادمین نداره) | فقط مشاهده‌ی محتوا |
| `device` | خودِ اپلیکیشن کیوسک (نه پنل ادمین) | فقط `GET /contents/vitrin` (ویترین خودش) و `GET /contents/local`/`scrap`/`{id}` برای محتوای خودش |

⚠️ **نکته‌ی مهم برای طراحی UI پنل ادمین**: با نقش `operator` نمی‌شه دستگاه
جدید ساخت، دستگاه‌ها رو لیست/ویرایش/حذف کرد، یا به دستگاه دستور بلادرنگ
فرستاد — این‌ها همه **فقط `admin`**. اگه بخواید اپراتورها هم این کارها رو
بکنن، باید سمت بک‌اند این محدودیت عمداً باز بشه (فعلاً دست نزدم چون یک
تصمیم دسترسی‌دهیه).

همه‌ی اندپوینت‌های زیر (به‌جز لاگین) نیاز به این هدر دارن:
```
Authorization: Bearer <access_token>
```
فرمت خطای همیشگی:
```json
{ "error": "متن پیام فارسی" }
```

## ۲. احراز هویت و مدیریت کاربران

### `POST /auth/login` 🔓 عمومی
```json
// body
{ "username": "admin1", "password": "********" }
```
```json
// 200
{ "access_token": "...", "refresh_token": "..." }
```

### `POST /auth/refresh` 🔓 عمومی
```json
{ "refresh_token": "..." }
```
→ همون شکل پاسخ لاگین (توکن‌های جدید، rotate شده).

### `POST /auth/logout` 🔒 هر کاربر لاگین‌شده
بدون بدنه. رفرش‌توکن کاربر جاری رو باطل می‌کنه.

### `GET /auth/profile` 🔒 هر کاربر لاگین‌شده
```json
// 200
{
  "id": 1,
  "status": true,
  "username": "admin1",
  "name": "مدیر سیستم",
  "role": "admin",
  "location": "",
  "section": ""
}
```

### مدیریت کاربران — فقط `admin`

| هدف | Method | مسیر |
|---|---|---|
| ساخت کاربر جدید | POST | `/auth/users` |
| لیست همه‌ی کاربران | GET | `/auth/users` |
| ویرایش کاربر | PUT | `/auth/users/{id}` |
| حذف کاربر | DELETE | `/auth/users/{id}` |

**`POST /auth/users` body:**
```json
{
  "username": "operator1",
  "password": "MinLen8Chars",
  "role": "operator",
  "name": "اپراتور محتوا"
}
```
`role` باید یکی از `admin` / `operator` / `user` / `device` باشه.

> ⚠️ برای ساخت کاربر نقش `device` این اندپوینت رو مستقیم صدا نزنید — کاربر
> مربوط به یک کیوسک باید از طریق `POST /devices` ساخته بشه (پایین‌تر)، چون
> اونجا کاربر و دستگاه با هم و با پیوند درست ساخته می‌شن.

**`GET /auth/users` → 200:** آرایه‌ای از `ProfileResponse` (همون شکلی که در
`/auth/profile` دیدید).

**`PUT /auth/users/{id}` body** (همه‌ی فیلدها اختیاری، فقط چیزی که می‌فرستید
عوض می‌شه):
```json
{ "name": "نام جدید", "is_active": false, "role": "operator", "password": "New8CharsPass" }
```

**`DELETE /auth/users/{id}`** → بدون بدنه.

## ۳. مدیریت دستگاه‌ها (کیوسک‌ها) — فقط `admin`

### `POST /devices` — ساخت کیوسک جدید
با این یک درخواست هم کاربر (نقش `device`) و هم رکورد دستگاه با هم ساخته
می‌شن:
```json
{
  "user": {
    "username": "kiosk-lobby-1",
    "password": "MinLen8Chars",
    "role": "device",
    "name": "کیوسک لابی"
  },
  "name": "کیوسک لابی اصلی",
  "location": "طبقه همکف - ورودی اصلی ساختمان مرکزی",
  "section": "ساختمان مرکزی",
  "mac_address": "AABBCCDDEEFF",
  "ip_address": "192.168.1.50",
  "config": {}
}
```
نکات validation:
- `mac_address` دقیقاً باید ۱۲ کاراکتر باشه (بدون `:`/`-`).
- `location` بین ۲۰ تا ۲۰۰ کاراکتر.
- `config` یک JSON آزاد (`jsonb`) برای هر تنظیمات اضافه‌ی دستگاهه؛ فعلاً هیچ
  ساختار مشخصی روش اعمال نشده.

→ `201` با پیام موفقیت. برای گرفتن `id` دستگاه تازه‌ساخته‌شده، بعدش
`GET /devices` رو صدا بزنید (چون `POST` خودِ id رو برنمی‌گردونه).

### `GET /devices` — لیست همه‌ی کیوسک‌ها
```json
[
  {
    "id": 1,
    "name": "کیوسک لابی اصلی",
    "location": "طبقه همکف - ورودی اصلی ساختمان مرکزی",
    "section": "ساختمان مرکزی",
    "mac_address": "AABBCCDDEEFF",
    "ip_address": "192.168.1.50",
    "status": "active",
    "last_seen": "2026-09-05T09:00:00Z",
    "config": {},
    "created_at": "2026-01-01T00:00:00Z"
  }
]
```
`status` یکی از `active` / `offline` / `maintenance` — و خودش با اتصال/قطعِ
Socket.IO کیوسک به‌روز می‌شه (نیازی به تنظیم دستی نیست، مگه بخواید حالت
`maintenance` رو دستی ست کنید).

### `PUT /devices/{id}` — ویرایش
همه‌ی فیلدها اختیاری (فقط چیزی که می‌فرستید عوض می‌شه):
```json
{ "name": "نام جدید", "status": "maintenance", "location": "...", "config": {} }
```
> توجه: این اندپوینت کاربرِ لینک‌شده (username/password کیوسک) رو تغییر
> نمی‌ده — فقط فیلدهای خودِ دستگاه.

### `DELETE /devices/{id}` — حذف کیوسک
بدون بدنه.

### `POST /devices/{id}/commands` — ارسال دستور بلادرنگ به کیوسک
این از طریق اتصال Socket.IO زنده‌ی کیوسک یک پیام فوری می‌فرسته (بدون نیاز به
اینکه کیوسک پولینگ کنه). اگه کیوسک همین الان آنلاین/متصل نباشه، خطای
`409 Conflict` می‌گیرید (`"دستگاه در حال حاضر به سرور متصل نیست"`).

```json
// body
{ "type": "open_admin_panel", "payload": {} }
```
فعلاً تنها `type` ای که سمت اپ کیوسک (Flutter) هندل می‌شه
`"open_admin_panel"` هست (باز کردن پنل ادمین روی خودِ کیوسک بدون نیاز به رمز
دستی) — چون این مکانیزم عمومیه، هر `type`/`payload` دیگه‌ای هم که بعداً سمت
کیوسک اضافه بشه از همین یک اندپوینت قابل ارسال خواهد بود.

## ۴. مدیریت محتوا

دو منبع محتوا داریم که هر دو زیر یک مدل مشترک (`Content`) هستن ولی رفتار
متفاوتی دارن:

| | محتوای **لوکال** (`source: "daralouOperator"`) | محتوای **اسکرپ‌شده** (`source: "daralouWeb"`) |
|---|---|---|
| منبع | ادمین/اپراتور از پنل می‌سازه | خودکار از سایت شرکت اسکرپ می‌شه |
| قابل ساخت/ویرایش/حذف؟ | ✅ بله (`operator`+`admin`) | ❌ نه — اندپوینت‌های ویرایش/حذف صراحتاً رد می‌کنن |
| مختص یک دستگاه خاص؟ | بله، موقع ساخت به یک یا چند `device_id` اساین می‌شه | نه، سراسریه برای همه‌ی دستگاه‌ها یکسانه |

### `GET /contents/local?device_id={id}&page=&size=` — لیست محتوای لوکال یک دستگاه
نقش مجاز: `admin`, `operator` (باید `device_id` بفرستن؛ خودِ کیوسک هم می‌تونه
بدون `device_id` صدا بزنه، خودکار محتوای خودش میاد).

```json
// 200
{
  "content": [
    { "id": 42, "title": "اطلاعیه تعطیلی نیمه‌روز", "summary": "به مناسبت ...",
      "main_img": "/static/uploads/xyz.jpg", "created_at": "2026-09-01T10:00:00Z" }
  ],
  "total": 3, "page": 1, "size": 20
}
```

### `GET /contents/scrap?page=&size=` — لیست اخبار اسکرپ‌شده
سراسریه، نیازی به `device_id` نیست. همون شکل پاسخ بالا.

### `GET /contents/{content_id}?device_id={id}` — جزئیات یک محتوا
```json
// 200
{
  "id": 42, "content_type": "announcement", "title": "...", "body": "متن کامل ...",
  "summary": "...", "main_img_url": "/static/uploads/xyz.jpg",
  "extra_img_list": ["/static/uploads/a.jpg"], "external_url": "",
  "source": "daralouOperator", "start_date": null, "end_date": null,
  "is_published": true, "created_by": 7,
  "CreatedAt": "2026-09-01T10:00:00Z", "UpdatedAt": "2026-09-01T10:00:00Z"
}
```
> ⚠️ **Quirk موجود در کد**: همه‌ی فیلدها snake_case هستن به‌جز دو فیلد آخر
> که camelCase/PascalCase برمی‌گردن: `CreatedAt` و `UpdatedAt`.

اگه محتوا لوکال باشه، `device_id` باید همون دستگاهی باشه که این محتوا بهش
اساین شده وگرنه `403` می‌گیرید. برای اسکرپ‌شده این چک انجام نمی‌شه.

### `POST /contents` — ساخت محتوای لوکال جدید — `operator`/`admin`
```json
{
  "title": "اطلاعیه تعطیلی نیمه‌روز",
  "body": "متن کامل اطلاعیه (۲۰ تا ۲۰۰۰ کاراکتر)...",
  "summary": "خلاصه (اختیاری)",
  "main_img": "/static/uploads/xyz.jpg",
  "img_list": ["/static/uploads/a.jpg", "/static/uploads/b.jpg"],
  "device_id": [1, 3],
  "start_date": null,
  "end_date": null
}
```
- `content_type` این محتوا همیشه خودکار `"announcement"` ست می‌شه (سمت
  بک‌اند ثابته، شما چیزی برای این فیلد نمی‌فرستید).
- `device_id` آرایه‌ست — یعنی می‌شه یک محتوا رو همزمان به چند کیوسک اساین
  کرد.
- `img_list` باید حداقل یک آیتم داشته باشه.

> 🚧 **یک نکته‌ی مهم و باز (Open Gap)**: در کل بک‌اند **هیچ اندپوینت آپلود
> فایل/تصویر پیدا نشد** (نه multipart، نه `/upload`). یعنی `main_img` و
> `img_list` انتظار دارن از قبل یک URL/مسیر معتبر (مثلاً `/static/...`)
> بهشون بدید، ولی فعلاً هیچ راهی برای «آپلود کردن یک فایل از کامپیوتر ادمین
> و گرفتن این URL» وجود نداره. قبل از پیاده‌سازی فرم «ساخت محتوای لوکال» در
> فرانت، این مورد باید حل بشه (یا یک اندپوینت آپلود جدید اضافه کنیم، یا
> تصمیم بگیرید تصاویر از جای دیگه‌ای هاست می‌شن و فقط URL خارجی وارد
> می‌شه). بگید کدوم مسیر رو ترجیح می‌دید تا برات اضافه‌ش کنم.

→ `201` با پیام موفقیت (باز هم id تازه‌ساخته رو برنمی‌گردونه؛ برای گرفتنش
باید دوباره `GET /contents/local?device_id=` رو صدا بزنید).

### `PUT /contents/{id}` — ویرایش محتوای لوکال — `operator`/`admin`
فقط روی محتوای لوکال کار می‌کنه (روی اسکرپ‌شده `400` با پیام
`"محتوا اسکرپ شده قابل تغییر نیست!"` می‌گیرید). همه‌ی فیلدها اختیاری:
```json
{ "title": "عنوان جدید", "body": "...", "img_list": ["..."], "start_date": null }
```
> توجه: از این اندپوینت نمی‌شه لیست `device_id` (اینکه به کدوم دستگاه‌ها
> اساین شده) رو تغییر داد — فقط موقع ساخت (`POST`) قابل تنظیمه. اگه نیاز به
> تغییر اساینمنت بعد از ساخت دارید، بگید تا این قابلیت رو اضافه کنم.

### `DELETE /contents/{id}` — حذف محتوای لوکال — `operator`/`admin`
فقط روی محتوای لوکال کار می‌کنه (همون محدودیت بالا).

## ۵. مدیریت ویترین هر کیوسک

هر دستگاه یک ویترین جدا داره: تعدادی **اسلات شماره‌دار** (۱ تا `size`) که هر
کدوم می‌تونه صراحتاً به یک محتوا (لوکال یا اسکرپ‌شده) **پین** بشه؛ اسلات‌های
خالی خودکار با آخرین اخبار اسکرپ‌شده پر می‌شن. یعنی «کاملاً دستی»، «کاملاً
خودکار» و «ترکیبی» بدون نیاز به یک سوییچ جدا، فقط با همین یک مکانیزم پوشش
داده می‌شه.

نقش مجاز روی همه‌ی اندپوینت‌های این بخش: `admin`, `operator`.

### `GET /devices/{device_id}/vitrine` — تنظیمات فعلی
```json
{
  "size": 5,
  "items": [
    { "position": 1, "source": "daralouOperator",
      "content": { "id": 42, "title": "اطلاعیه تعطیلی نیمه‌روز", "summary": "...",
                   "main_img": "/static/uploads/xyz.jpg", "created_at": "2026-09-01T10:00:00Z" } },
    { "position": 3, "source": "daralouWeb",
      "content": { "id": 108, "title": "قیمت مس امروز اعلام شد", "summary": null,
                   "main_img": "/static/scrap/news108.jpg", "created_at": "2026-09-04T08:00:00Z" } }
  ]
}
```
فقط آیتم‌های **صراحتاً پین‌شده** برمی‌گرده (نه اسلات‌هایی که قراره خودکار پر
بشن — برای نتیجه‌ی نهایی به بخش «پیش‌نمایش» پایین‌تر مراجعه کنید). اگه هنوز
هیچ تنظیمی برای این دستگاه نشده، `items: []` و `size: 5` (پیش‌فرض) برمی‌گرده.

### `PUT /devices/{device_id}/vitrine` — ذخیره (جایگزینی کامل)
```json
{
  "size": 5,
  "items": [
    { "position": 1, "content_id": 42 },
    { "position": 3, "content_id": 108 }
  ]
}
```
هر بار **کل چینش** با این درخواست جایگزین می‌شه (نه افزایشی). برای «کاملاً
خودکار کردن ویترین»، `items: []` بفرستید.

قوانین اعتبارسنجی:

| قانون | خطا |
|---|---|
| `size` بین ۱ تا ۲۰ | `400` |
| `position` بین ۱ تا `size` | `400` – `"جایگاه X خارج از بازه‌ی ویترین (۱ تا N) است"` |
| `position` تکراری نباشه | `400` – `"جایگاه X بیش از یک بار تکرار شده است"` |
| `content_id` باید وجود داشته باشه | `400` – `"محتوای شماره X یافت نشد"` |
| محتوای **لوکال** باید از قبل به همین `device_id` اساین شده باشه | `400` – `"محتوای لوکال شماره X به این دستگاه اختصاص داده نشده است"` |
| محتوای **اسکرپ‌شده** محدودیت نداره | — |

→ `200`: `{ "message": "تنظیمات ویترین با موفقیت ذخیره شد" }`

### `GET /devices/{device_id}/vitrine/preview` — پیش‌نمایش نتیجه‌ی نهایی
همون چیزی که خودِ کیوسک می‌بینه — پین‌شده‌ها + اسلات‌های خالی که خودکار با
اخبار پر شدن:
```json
{
  "items": [
    { "position": 1, "source": "daralouOperator", "is_auto": false,
      "content": { "id": 42, "title": "...", "summary": "...", "main_img": "...", "created_at": "..." } },
    { "position": 2, "source": "daralouWeb", "is_auto": true,
      "content": { "id": 205, "title": "آخرین خبر اسکرپ‌شده", "summary": null, "main_img": "...", "created_at": "..." } }
  ]
}
```
`is_auto: true` یعنی این اسلات خالی بوده و خودکار با آخرین خبر پر شده.
بعد از هر `PUT` موفق، این اندپوینت رو صدا بزنید تا نتیجه‌ی نهایی رو به ادمین
نشون بدید.

## ۶. فلوهای کامل (End-to-End) که ادمین انجام می‌ده

### فلو ۱: راه‌اندازی یک کیوسک جدید از صفر
۱. `POST /devices` → ساخت کاربر+دستگاه.
۲. `GET /devices` → پیدا کردن `id` دستگاه تازه‌ساخته‌شده.
۳. (اختیاری) `POST /contents` با `device_id: [همون id]` → ساخت چند محتوای
   لوکال مخصوص این کیوسک.
۴. `PUT /devices/{id}/vitrine` → چیدن ویترین این کیوسک.
۵. `GET /devices/{id}/vitrine/preview` → تایید نتیجه.

### فلو ۲: مدیریت روزمره‌ی محتوا (اپراتور، بدون دسترسی به دستگاه‌ها)
۱. `GET /contents/local?device_id=X` و `GET /contents/scrap` → مرور محتوای
   موجود.
۲. `POST /contents` → ساخت اطلاعیه‌ی جدید برای یک یا چند کیوسک.
۳. `PUT /devices/X/vitrine` → پین کردن اطلاعیه‌ی تازه توی یک جایگاه خاص از
   ویترین.

### فلو ۳: باز کردن پنل ادمین روی خودِ کیوسک (بدون رمز دستی)
۱. `POST /devices/{id}/commands` با `{ "type": "open_admin_panel", "payload": {} }`
   → اگه کیوسک آنلاینه، فوراً پنل روش باز می‌شه؛ اگه آفلاینه `409` می‌گیرید.

---

## ۷. مسائل باز / نیاز به تصمیم قبل از پیاده‌سازی فرانت

این‌ها رو باید قبل یا حین پیاده‌سازی UI حل کنیم:

1. **آپلود تصویر برای محتوای لوکال** — فعلاً هیچ اندپوینتی نداریم. نیاز به
   یک `POST /uploads` (یا مشابه، multipart) داریم که فایل بگیره و یک
   `main_img`/آیتم `img_list` قابل‌استفاده برگردونه.
2. **دسترسی `operator` به `GET /devices`** — الان این اندپوینت (و کل CRUD
   دستگاه‌ها) فقط `admin`ه. اگه اپراتورها هم باید از صفحه‌ی «انتخاب کیوسک
   برای تنظیم ویترین» استفاده کنن، این محدودیت باید حداقل برای `GET /devices`
   (لیست، نه ساخت/حذف) به `operator` هم باز بشه.
3. **گرفتن `id` بعد از ساخت** — `POST /devices` و `POST /contents` فقط پیام
   موفقیت برمی‌گردونن، نه رکورد ساخته‌شده. فرانت باید بعدش خودش لیست رو
   دوباره بگیره (یا اگه بخواید، می‌تونم این دو اندپوینت رو عوض کنم که خودِ
   رکورد ساخته‌شده (با `id`) رو هم برگردونن).
4. **تغییر اساینمنت دستگاه‌های یک محتوای لوکال بعد از ساخت** — الان
   `PUT /contents/{id}` نمی‌تونه لیست `device_id` رو عوض کنه؛ فقط موقع ساخت
   قابل تنظیمه.

اگه بخواید همین الان هر کدوم از این ۴ مورد رو حل کنم، بگید کدوم‌ها اولویت
دارن.
